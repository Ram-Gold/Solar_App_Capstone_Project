# Over-permissive RLS policies allow anonymous deletes/updates and customer-role privilege escalation

## Problem & Verification
Verified directly against live Supabase `pg_policies` on project `gkrdwzbxpstpqpvqlwbt`:

1. **`quote_tickets`**: `"Public update access for quote_tickets"` (`roles={public}, qual=true`) and `"Public delete access for quote_tickets"` (`roles={public}, qual=true`) allow any anonymous client to alter statuses/reservations or delete any inquiry.
2. **`customers`**: `"Public token access on customers"` (`roles={anon}, qual=true`) exposes all customer rows (`phone_number`, `email`, `access_token`) to `anon` `SELECT`, and `"Customer can delete own row"` (`roles={anon}, qual=true`) allows `anon` to delete any customer row.
3. **`customer_purchases` & `warranty_claims`**: `"Staff and Admin full access on customer_purchases"` and `"Staff and Admin full access on warranty_claims"` check only `roles={authenticated}` with `qual=true / with_check=true` without `get_user_role() IN ('staff', 'admin')`—so any authenticated **customer** can directly update their `warranty_expires_at`, unvoid their unit, approve their own `warranty_claims`, or delete records. `Public access on customer_purchases` and `Public select/insert on warranty_claims` also allow `anon` unrestricted reads/inserts.
4. **`products`**: `"Admin can manage products"` (`ALL`, `qual=(auth.role() = 'authenticated')`) grants `DELETE`/`ALL` to any authenticated user (including `staff` and `customer`), contradicting `"Admin delete products"` and Staff role restrictions.

## Agent Brief

**Category:** bug
**Summary:** Replace permissive public/authenticated RLS policies with role-scoped access and migrate customer portal token operations to SECURITY DEFINER RPCs

**Current behavior:**
Live Supabase RLS policies currently allow `anon` / `public` clients to update or delete `quote_tickets`, select or delete `customers`, and read or insert `customer_purchases` and `warranty_claims`. Authenticated customer accounts (`auth.uid()` not in `admins` or `staff`) match broad `(auth.role() = 'authenticated')` / `true` policies on `products`, `customer_purchases`, and `warranty_claims`, allowing direct writes or deletes from the client SDK. Meanwhile, several customer portal helpers in `customerService` use direct table fallbacks when run anonymously or as a customer.

**Desired behavior:**
1. Tighten live Postgres RLS policies via `supabase_mcp` `apply_migration`:
   - `quote_tickets`: allow public/anon `INSERT` only (`QuoteModal`), restrict `SELECT`, `UPDATE`, and `DELETE` to `get_user_role() IN ('staff', 'admin')`.
   - `customers`: restrict `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on direct table access to `get_user_role() IN ('staff', 'admin')`, plus `SELECT` (`auth.uid() = user_id`) for authenticated customers reading their own record.
   - `customer_purchases` & `warranty_claims`: restrict direct `INSERT`/`UPDATE`/`DELETE` and full `SELECT` to `get_user_role() IN ('staff', 'admin')`, plus own-row `SELECT` for authenticated customers (`customer.user_id = auth.uid()`).
   - `products`: remove `"Admin can manage products"` (`auth.role() = 'authenticated'`); allow public `SELECT`, allow `staff` and `admin` `INSERT`/`UPDATE`, and restrict `DELETE` strictly to `get_user_role() = 'admin'`.
2. Ensure all token-scoped customer self-service operations run cleanly through `SECURITY DEFINER` Postgres RPCs rather than raw direct table mutations:
   - Customer portal read (`get_customer_portal_data`), claim submission (`submit_warranty_claim`), account activation (`activate_customer_account`), email confirmation sync (`confirm_customer_email`), and customer self-account deletion (`delete_own_customer_account`).
   - Update client helpers in `customerService` to invoke those RPCs without falling back to unrestricted direct table mutations.

**Key interfaces:**
- Live Supabase RLS policies and `get_user_role()` function inspected and updated via `supabase_mcp`
- New `SECURITY DEFINER` RPCs: `confirm_customer_email(p_token uuid, p_email text)` and `delete_own_customer_account(p_token uuid)` with least-privilege `GRANT EXECUTE`
- Customer self-service functions in `customerService` (`fetchCustomerPortalData`, `confirmCustomerEmail`, `setCustomerPassword`, `deleteCustomerAccount`, `submitWarrantyClaim`)

**Acceptance criteria:**
- [ ] Unauthenticated (`anon`) requests cannot `SELECT`, `UPDATE`, or `DELETE` `customers`, `quote_tickets`, `customer_purchases`, or `warranty_claims` directly
- [ ] Authenticated customer users cannot update `products`, `customer_purchases`, or `warranty_claims` directly via PostgREST
- [ ] Staff users can insert/update products and manage inquiries/customers/claims, while `DELETE` on `products` is denied for non-admins at the RLS layer
- [ ] Guest quote submission, customer portal load (`get_customer_portal_data`), email confirmation, password setup, warranty claim submission, and self-delete account flows all continue to pass verification

**Out of scope:**
- Changing admin/staff table schemas or moving away from token-plus-Auth dual customer portal sign-in
